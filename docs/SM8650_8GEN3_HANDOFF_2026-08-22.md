Этот документ предназначен для нового контекстного окна Codex. Продолжать работу нужно строго по отдельной ветке Snapdragon 8 Gen 3 / SM8650 / Cortex-X4 / Adreno 750. Главная цель — исправить пропадающую геометрию и поднять Bloodborne с текущих 5–6 FPS до стабильных 25–30 FPS, не изменив поведение Snapdragon 8 Gen 5 / Adreno 840 и Mali.

## Обязательная аппаратная изоляция

1. Все новые Vulkan-решения разрешены только для точной пары:

   - vendorID = 0x5143
   - deviceID = 0x43051401

   Это Adreno 750.

2. Для решений, относящихся к фирменному драйверу Qualcomm, дополнительно требуется driverFamily == qualcomm-proprietary.

3. CPU/FEX-политики разрешены только при одновременном выполнении:

   - ro.soc.model равен exact SM8650;
   - обнаружен MIDR Cortex-X4: implementer 0x41, part 0xD82;
   - hostOsFeatures не содержит hardware TSO.

4. Запрещены общие условия:

   - Adreno 7xx;
   - любой Qualcomm;
   - любой ARM или Cortex;
   - deviceName/substring вместо точного ID.

5. Для каждого нового условия обязательны отрицательные тесты:

   - A840: vendor 0x5143, device 0x44050a31;
   - Mali: vendor 0x13b5;
   - SM8750/Oryon/hardware TSO;
   - неизвестные или неполные ID.

   Их прежние значения policy, capability, cache namespace и runtime path должны оставаться неизменными.

6. Запрещено вливать изменения в прежние ветки 8 Gen 5/Mali или отправлять их в remote. Создать отдельные локальные ветки, например:

   - parent: work/sm8650-a750-only-20260822
   - funnel-arm: work/sm8650-a750-vulkan-only-20260822

7. Нельзя делать reset, checkout файлов, clean или массово откатывать грязное дерево. Все существующие изменения считать пользовательскими или относящимися к текущей работе.

8. Устройство нельзя выключать или перезагружать. Приложение разрешено перезапускать только для контролируемых A/B, которым нужен fresh PID. Кэши не очищать без отдельного доказанного эксперимента.

## Доказанные результаты

### Прогретый Qualcomm + FEX + MOBILE80

- FEX blocks: +0/s;
- steady FPS: 5–6;
- draw: примерно 3.8–5.8k/s;
- submit: примерно 60–79/s;
- present: примерно 5–6/s.

Следовательно, низкий steady FPS не объясняется прогрузкой FEX-блоков.

### Стоимость компилятора FEX

- warm: около 99 ms за 120 секунд, 0.082% одного ядра;
- cold: около 1.47 s, 1.23% одного ядра.

Компиляция FEX не объясняет 5 FPS.

### Главное измеренное узкое место

- около 4,842 синхронных PageManager→GpuComm invalidation/s;
- около 2.46 blocked-thread-seconds на секунду;
- readback batching тратит значительное время на GPU completion/timeline waits;
- GP cache generation miss возникает почти на каждом lookup;
- GPU busy около 42%;
- RSS рос примерно 0.54→4.02 GB с большим swap/reclaim.

### PMU baseline

- 44.76G instructions;
- 36.96G cycles;
- IPC около 1.21;
- около 2.78 занятых CPU;
- 134k context switches;
- 67.8k migrations;
- 38.5k faults.

### Hot telemetry gate

Отключение всегда включённой rasterizer timing/atomic telemetry не изменило steady 5 FPS. Патч убирает диагностический шум из hot path, но не является главным ускорением.

### MemcpySetTSO=false A/B

- FEX выбрал configureFlags=2;
- namespace: ...-ab-mtso0-sm-swtso;
- scalar TSO и HalfBarrier остались включены;
- проверенный кадр был целым;
- FPS остался 5.

Не продвигать этот флаг в production: ускорение не доказано. Единичный целый кадр не доказывает исправление геометрии.

### MOBILE60

MOBILE60 / 960x544 регулярно показывает значительно больше дыр в геометрии. Все дальнейшие сравнения проводить на MOBILE80. Не смешивать resolution defect с A750/FEX defect.

### Turnip на A750

Mesa 26.2.0:

- прошла import/probe;
- была hardware-bound к A750;
- затем в Bloodborne получила ErrorDeviceLost;
- present упал до 0;
- геометрия стала хуже.

Mesa 26.2.1 ранее давала красный треугольник и около 2 FPS. Пока оставить Qualcomm system default.

### BDA dedicated A/B

При удалении только этого marker и fresh PID dedicated-фаза дошла далеко в запуск, затем:

Запрещено внедрять A750 always-dedicated BDA на основании прежней гипотезы. Причинность BDA не доказана, а dedicated-конфигурация упала.

### Новая гипотеза корректности

Фирменный A750-драйвер имеет дефект или несовместимость в vkCmdPipelineBarrier2. Tombstone подтверждает место падения, но ErrorDeviceLost мог быть вторичным следствием более ранней ошибки.

Проверять только controlled A/B для exact:

    vendorID == 0x5143
    deviceID == 0x43051401

Не применять legacy synchronization к Turnip, A840 или Mali.

## Дополнение Codex: состояние на 2026-08-22 09:32

Цель 25 FPS и полностью корректная картинка **не достигнута**. Не считать
нижеописанный результат исправлением пола: финальная точка сохранения ставит

### Уже принятые SM8650-ограничения

- Immutable SRT на SM8650 оказался причиной крупных исчезновений пола и целых
  участков геометрии. Exact-SM8650 guard теперь игнорирует оставшийся marker;
  A840/Gen5 сохраняет прежний путь.
- Exact SM8650 + software TSO использует synchronous PageManager. В matched A/B
  это поднимало Bloodborne примерно с 2 FPS до 8–11 FPS и давало более целую
  картинку, но кратковременные дыры/чёрные прямоугольники остались.
- `run-fast-bulk-guest-write` и `run-suballocate-bda-buffers` обязательны.
  Отключение первого останавливало прогресс/давало чёрный кадр; dedicated BDA
  приводил к device-lost/SIGSEGV внутри proprietary driver.

### Отклонённый FEX fast-pin A/B

Software-TSO unaligned atomic проходит цепочку:

    SIGBUS alignment -> deferred helper -> InterruptFaultPage ->
    SIGSEGV safepoint -> HostSignalCapture -> ThreadStop -> release pin

`deferredPhase=3` означает `ResumeOriginal`. Поток SIGSEGV `code=2` с адресом
interrupt page является внутренним release-token протоколом, а не гостевым
crash. Временный exact-SM8650 fast release-pin path сохранял decoded guest RIP,
но остановил гостевой прогресс:

- A/B остановился на release-only sequence 64, чёрный экран/0 FPS;
- control той же сборки дошёл до capture sequence 512 примерно за 6.5 s и title
  на 29–32 FPS.

Fast-pin код и marker `run-sm8650-fex-fast-pin-release-ab` полностью удалены.
После удаления FEX runtime/adapter пересобраны; host tests: 12/12. Артефакты:
`.codex-sm8650-fastpin-static-01.png` ... `08.png` и
`.codex-sm8650-fastpin-control-static-01.png` ... `08.png`.

### Transfer/readback и отклонённый scoped-upload A/B

Baseline почти не batch-ит transfers. Ранее в gameplay:

    queued=2478075 flushes=2199552 copyCalls=2404891
    origin=h:640824,u:1306823,g:530428

Около 89% запросов завершались отдельным flush. Upload-origin при FEX намеренно
не входит в `BeginBufferUploadBatch()`: отложенный copy не продлевает lifetime
staging/ring allocation. Старый remote подтверждает более простой
immediate-materialization путь, но откатывать renderer/FEX/driver изменения
нельзя.

Readback не сообщает логических отказов, но дорог: в прежнем стабильном логе
при `snapshots=5376` были `fallbacks=0`, `publishFailures=0`, `gpuDirtyMiss=0`,
но `timelineWaits=34676` и накопленный `gpuCompletionMs=939862.370`.

Был временно проверен отдельный capability-guarded scoped-upload A/B только для
точного proprietary A750. Результат:

- control дошёл до title/gameplay; gameplay: `queued=467662`,
  `flushes=430080` (около 92%);
- A/B действительно объединял первые uploads (`queued=2`, `flushes=1`), но
  позднее дал лишь около 85–88% flush/request;
- на 2:27–2:34 восемь кадров подряд показывали чёрный экран со spinner при
  живом PID, 30–32 present/s и `FEX blocks +0/s`; control к этому времени давно
  был в title/gameplay;
- device-lost/crash не было: это регресс публикации ресурсов/прогресса.

Эксперимент отклонён. Exact marker `run-sm8650-fex-scoped-upload-batch-ab`,
общий `run-bisect-enable-vk-scoped-upload-batch` и весь временный код удалены.
Не повторять scoped/cross-request staging batching без доказанного lifetime
контракта.

### Реальные механизмы GameHub и Winlator

Исследован APK GameHub с подключённого устройства:

- SHA-256:
  `50DA9659677823AA63074A732F0280CDCBD386E05146C939845FFCEEC5A1E055`;

- ключевые классы: `TemplateFexConfigKt`, `FEXConfig`, `FEXConfigData`,
  `TemplateBoxConfigKt`, `Box64Config`.

GameHub действительно содержит FEX и Box64 profiles. Его FEX defaults:

    Multiblock=1 MaxInst=5000 TSO=1 VectorTSO=0 MemcpySetTSO=0
    HalfBarrier=1 VolatileMetadata=1 X87ReducedPrecision=0
    SmallTSC=1 SMC=mtrack MonoHacks=1 ForceSVEWidth=0

Раскодированные GameHub FEX-шаблоны:

- Extreme: Multiblock on, TSO/vector/memcpy/half-barrier off,
  volatile metadata on, reduced-x87 on;
- Performance: Multiblock on, TSO/half-barrier/volatile metadata on,
  vector/memcpy off, reduced-x87 on;
- Stable: Multiblock off, TSO/half-barrier/volatile metadata on,
  vector/memcpy off, reduced-x87 off;
- Compatibility: Multiblock off, TSO/vector/memcpy/half-barrier/volatile
  metadata on, reduced-x87 off.

Текущий LSX4 FEX по memory precision соответствует Compatibility и дополнен
exact Cortex-X4/DynamicL1 адаптацией. `ForceSVEWidth=0` в GameHub означает auto,
а не скрытую оптимизацию; автоматический SVE128 path у нас уже есть. FEX upstream
также задаёт `Multiblock=true`, `MaxInst=5000`, но прямо предупреждает о более
долгой компиляции/stutter. `X87ReducedPrecision` upstream по умолчанию false и
прямо предупреждает о возможных rendering bugs:
`https://github.com/FEX-Emu/FEX/blob/main/FEXCore/Source/Interface/Config/Config.json.in`.

GameHub Box64-шаблоны используют тот же класс компромиссов: большие блоки,
direct CALL/RET и native flags для скорости, затем fast NAN/rounding, x87 и
ослабление strong-memory для более агрессивных профилей. Официальный Winlator
Performance preset задаёт:

    SAFEFLAGS=1 FASTNAN=1 FASTROUND=1 X87DOUBLE=0 BIGBLOCK=3
    STRONGMEM=0 FORWARD=512 CALLRET=1 WAIT=1 NATIVEFLAGS=1 WEAKBARRIER=2

Источник:
`https://github.com/brunodev85/winlator-app/blob/main/app/src/main/java/com/winlator/box64/Box64PresetManager.java`.
Документация Box64 прямо называет большие блоки способом ускорения, а
`STRONGMEM=0` -- отсутствием специальной эмуляции сильной x86 memory model:
`https://github.com/ptitSeb/box64/blob/main/docs/USAGE.md`.

Соответствие механизмов:

- Box64 `BIGBLOCK/FORWARD` примерно соответствует FEX
  `Multiblock/MaxInst`; `MaxInst=5000` у нас уже есть;
- Box64 `CALLRET` соответствует уже существующим FEX shadow-stack/direct-link
  путям;
- `NATIVEFLAGS/SAFEFLAGS` соответствует уже используемым FEX deferred flags и
  ARM `FLAGM/FLAGM2`;
- `FASTNAN/FASTROUND/X87ReducedPrecision` меняют численную точность и до
  исправления изображения неприемлемы;
- `STRONGMEM=0`, weak barriers, отключение VectorTSO/MemcpySetTSO могут нарушать
  публикацию PS4 x86 ресурсов между guest CPU и GPU;
- aligned-only atomics неприемлемы: ранее уже получен `BUS_ADRALN`;
- compile-wait не является найденным bottleneck: warm FEX compilation в текущих
  профилях мала относительно PageManager/GpuComm/timeline waits.

Главный отсутствующий у нас GameHub performance switch -- Multiblock. Однако
точный SM8650 A/B уже дал только 6--8 FPS и усилил кратковременную потерю пола.
В серии `.codex-sm8650-fex-ab-multiblock-series-move-01.png` ... `08.png` кадр
03 теряет большую область пола, тогда как соседние кадры восстанавливают её.
Следовательно, слепо переносить GameHub Performance/Extreme нельзя.
